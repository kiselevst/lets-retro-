# Let's Retro

Ретро-доска команды. Миграция с HTML-прототипа (`window.storage` + polling) на
Next.js 15 + Supabase (Realtime, без polling).

## Статус миграции

- [x] Этап 1 — скелет репозитория, Supabase-клиент, первая SQL-миграция
- [x] Этап 2 — RLS-политики (открытые, без Auth — осознанное решение для MVP), `lib/types.ts`
- [x] Этап 3 — лендинг, создание доски, вход в комнату по ссылке / коду
- [x] Этап 4 — чтение доски (столбцы + карточки + участники) через Supabase Realtime
- [x] Этап 5 — добавление/редактирование/удаление карточек, голосование через интерфейс
- [x] Этап 6 — drag&drop склейка, SMART-оформление задач, «ретро закончилось»
- [x] Этап 7 — таймер, highlight-режим

- [ ] Этап 10 — полировка, README деплоя целиком

## Запуск локально

1. Создать проект на [supabase.com](https://supabase.com).
2. Скопировать `.env.example` → `.env.local`, вставить `NEXT_PUBLIC_SUPABASE_URL` и
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` из Project Settings → API.
3. Применить миграции из `supabase/migrations/` **по порядку** (0001 → 0002 → 0003 → 0004 → 0005 → 0006 → 0007) —
   через Supabase CLI (`supabase db push`) либо вставляя содержимое каждого файла
   в SQL Editor в дашборде и выполняя одну за другой.
4. `npm install`
5. `npm run dev` → http://localhost:3000

## Деплой на Vercel

1. Импортировать репозиторий в Vercel (Import Git Repository).
2. Добавить те же переменные окружения (`NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`) в Project Settings → Environment Variables.
3. Deploy. Дальше — `git push` на нужную ветку деплоит автоматически.

## Про безопасность (этап 2)

RLS включён на всех таблицах, но политики открытые (`USING (true)`) — без
Supabase Auth у Postgres нет возможности проверить, кто именно шлёт запрос.
Осознанный выбор для MVP с доверенной командой.

## Про identity (этап 3)

Без Supabase Auth: `participants.id` кладётся в `localStorage` браузера
(ключ per-board) при создании доски или входе по ссылке/коду.

## Про Supabase-клиент без generic-типизации

`lib/supabase.ts` намеренно не типизирован через `createClient<Database>(...)` —
ручное описание схемы приводило к ложным ошибкам компиляции. Типы из
`lib/types.ts` используются как обычные ручные касты (`as CardRow[]`).

## Про Realtime

Каждая таблица, за которой нужно следить в реальном времени, добавляется в
publication `supabase_realtime` отдельной миграцией. Таблицы, которые
фильтруются по не-первичному ключу (`board_id`), дополнительно переведены на
`REPLICA IDENTITY FULL` (`0005`) — без этого DELETE-события на такой таблице
не долетают вовремя, потому что в лог репликации по умолчанию попадает
только первичный ключ удалённой строки, и фильтр по `board_id` не может
сработать.

## Про голосование и position (этап 5)

- `position` карточек — `Date.now()` на клиенте; поэтому колонка `bigint`.
- Голос — строка в `votes` (уникальность `card_id + participant_id`);
  голосование = insert, снятие голоса = delete.
- Лимит голосов, self-vote и полное отключение голосования читаются из
  `board_settings` и проверяются на клиенте — RLS их не проверяет (тот же
  уровень доверия, что был в HTML-прототипе).

## Про склейку, SMART и завершение ретро (этап 6)

- **Склейка** — drag&drop карточки на другую **в том же столбце**: текст
  источника дописывается к цели через разделитель, `sources` копится для
  истории, карточка-источник удаляется целиком. Голоса источника при этом
  теряются (сознательное упрощение — см. комментарий в `lib/cards.ts`).
- **Экшн из карточки** — доступно только для столбцов кроме «Что делаем»;
  исходная карточка помечается `merged_into` и получает бейдж «Стало
  экшеном», рядом создаётся новая карточка в «Что делаем» с тем же текстом.
  Сразу после создания открывается модалка SMART — можно заполнить или
  пропустить, вернуться позже можно через кнопку 📋 на самой карточке.
- **Выполнено** — только у карточек в «Что делаем»; не зачёркивает текст, а
  показывает бейдж «✓ Готово» и слегка гасит карточку.
- **Ретро закончилось** — кнопка у модератора, ставит `board_settings.completed
  = true`. После этого все столбцы кроме «Что делаем» переходят в
  режим только для чтения (без добавления, редактирования, удаления,
  голосования и перетаскивания) — проверяется через проп `locked` в `Column`.

Новых миграций в этом этапе не потребовалось — все нужные поля
(`merged_into`, `sources`, `smart_*`, `done`, `board_settings.completed`)
были заложены ещё в самой первой схеме на этапе 1.

## Про таймер и режим подсветки (этап 7)

- **Таймер** хранится в `timer_state` (`ends_at` + `total_seconds`), меняется
  через `lib/timer.ts` (`startTimer`/`stopTimer`) и синхронизируется всем
  участникам через Realtime — потребовалась отдельная миграция `0006`,
  потому что раньше эту таблицу просто было незачем слушать. Обратный отсчёт
  на экране — обычный `setInterval` раз в секунду **только для отрисовки**,
  он не ходит в сеть — фактическое время хранится как абсолютная метка
  `ends_at`, а не как убывающий счётчик, поэтому не расходится между
  вкладками/учстниками с разной задержкой сети.
- **Режим подсветки при наведении** — единственная фича, которая работает
  не через таблицу в базе, а через Supabase Realtime **Broadcast**
  (`hooks/useHoverBroadcast.ts`): это чисто эфемерный сигнал "кто сейчас
  наводит курсор на какую карточку", ему незачем переживать перезагрузку
  страницы или засорять историю в БД. Включается через
  `board_settings.highlight_mode` — своего интерфейса для этого переключателя
  пока нет (появится на этапе 8, настройки), проверить можно, включив его
  вручную через SQL:
  ```sql
  update board_settings set highlight_mode = true where board_id = 'ID_ДОСКИ';
  ```

## Про настройки как intercepting route (этап 8)

`⚙ Настройки` в шапке комнаты (только у модератора) — это `<Link href="/r/[boardId]/settings">`. Next.js даёт два разных сценария на один и тот же адрес:

- Переход **изнутри** комнаты (клик по ссылке, обычная клиентская навигация) —
  Next.js перехватывает переход через `@modal/(.)settings/page.tsx` и
  показывает настройки как модалку поверх доски, без полной перезагрузки.
- Прямой заход по ссылке или обновление страницы (F5, когда открыт URL
  `/r/[boardId]/settings`) — сработает обычная страница
  `app/r/[boardId]/settings/page.tsx`, во весь экран.

Оба сценария рендерят один и тот же `components/SettingsContent.tsx` —
не дублируем логику, отличаются только обёртки (`SettingsModalClient` /
`SettingsPageClient`) и то, куда ведёт кнопка закрытия (`router.back()` у
модалки, `router.push('/r/[boardId]')` у полной страницы).

Для параллельного `@modal`-слота обязателен `app/r/[boardId]/layout.tsx`
(рендерит `{children}` и `{modal}`) и `@modal/default.tsx` (пустая заглушка
на случай, когда настройки не открыты) — без них Next.js не поймёт, что
делать со слотом на большинстве обычных страниц внутри `/r/[boardId]/*`.

## Про историю досок и ссылку-приглашение (этап 9)

Изначально на этом этапе планировался файловый экспорт/импорт (по аналогии с
HTML-прототипом), но раз результаты и так живут в Supabase бессрочно (пока
доску явно не удалили), от файла отказались в пользу более простого решения:

- **`lib/history.ts`** — список досок, которые модератор создавал **в этом
  браузере** (localStorage, ключ `lets-retro:my-boards`), без всякой
  аутентификации — та же логика идентичности, что и у `participantId`.
  Пополняется автоматически в момент создания доски (`app/create/page.tsx`).
- **`/history`** (`components/HistoryClient.tsx`) — показывает этот список,
  подтягивая для каждой записи живой статус из Supabase (число карточек,
  завершена ли), чтобы сразу было видно, какие доски ещё активны. Можно
  убрать доску из списка (не удаляя её саму) — вдруг список слишком длинный.
- **Ссылка-приглашение** — кнопка «🔗 Ссылка на доску» в шапке комнаты
  (только у модератора): на устройствах с нативным шерингом (Web Share API)
  открывает системное окно "Поделиться", иначе просто копирует ссылку в
  буфер обмена.

**Важно:** История — это просто список ссылок из localStorage конкретного
браузера, не общий для всех модераторов список "кто ещё создавал доски".
Если модератор откроет тот же аккаунт с другого устройства — список будет
пустым, хотя сами доски по ссылкам продолжат работать.

## Про тёмную/светлую тему

- Нейтральная "хром"-палитра (`bg`, `panel`, `line`, `ink` и т.д. в
  `tailwind.config.ts`) переведена на CSS-переменные (`app/globals.css`,
  `:root` для тёмной темы по умолчанию, `[data-theme='light']` для
  переопределений). Акцентные/семантические цвета (amber, teal, цвета
  столбцов) одинаковые в обеих темах — это выбор пользователя для
  конкретного элемента, а не часть оформления.
- Выбор темы хранится в `localStorage` (`lib/theme.ts`), переключатель —
  плавающая кнопка `components/ThemeToggleFloating.tsx` в правом нижнем углу
  **любой** страницы (не привязана к роли и не спрятана в настройках —
  первая версия была доступна только модератору внутри настроек доски,
  поправили сразу же, как заметили). Если пользователь ни разу не выбирал
  тему вручную — при первом заходе подхватывается тема устройства
  (`prefers-color-scheme`).
- В `app/layout.tsx` есть небольшой блокирующий inline-скрипт, который
  выставляет `data-theme="light"` на `<html>` **до** отрисовки страницы —
  без него при выбранной светлой теме была бы короткая вспышка тёмной темы
  при каждой загрузке (сервер не знает про localStorage, всегда рендерит
  значения по умолчанию из `:root`). У `<html>` стоит `suppressHydrationWarning`
  — без него React считает эту (ожидаемую) правку атрибута до гидратации
  ошибкой.
- Тень `shadow-panel` тоже через CSS-переменную (`--shadow-panel`) со своим
  значением на тему: та же тень, что хорошо смотрится на тёмном фоне, на
  светлом воспринимается глазом как яркое "свечение" по контуру панели —
  визуальная иллюзия на резкой границе размытой тени. На светлой теме тень
  сделана заметно мягче (меньше блюр, ниже непрозрачность).
- Рамка фокуса (`:focus-visible` в `globals.css`) — стандартная синяя рамка
  браузера почти не была видна на тёмном фоне и резала глаз на светлом;
  заменена на свою, спокойную, одинаковую в обеих темах.

## Про где хранятся результаты ретро

Все данные — в таблицах Supabase (Postgres), доступны по прямой ссылке на
доску сколько угодно долго, пока её не удалили явно через настройки.
"История" — это не хранилище результатов, а личный список закладок в
localStorage конкретного браузера.

**Важно для бесплатного тарифа Supabase:** проект приостанавливается после
7 дней без единого обращения к API — данные не теряются, но доска не
откроется, пока кто-то вручную не нажмёт Restore в дашборде Supabase. Для
команды с редкими ретро (раз в 1-2 недели и реже) это реальный сценарий.
Решения: разовый restore в дашборде, платный тариф Supabase (снимает
ограничение), либо периодический "пинг" проекта (cron/аптайм-монитор) —
задача на это заведена в `BACKLOG.md`.

## Про разъединение склеенных карточек

Склейка теперь обратима, но только для **последнего** шага — не вся история:

- При склейке (`lib/cards.ts: mergeCards`) в новое поле `cards.last_merge_snapshot`
  (jsonb, миграция `0007`) кладётся снимок: текст цели до склейки + списки
  `participant_id` всех, кто голосовал за цель и за источник на тот момент.
  Голоса обеих карточек при этом обнуляются — склеенная карточка стартует
  "с нуля", а не с суммой/пересечением голосов.
- При разъединении (`unmergeCard`) снимок читается: цели возвращается
  прежний текст и прежние голоса (по тем же `participant_id` — честное
  восстановление, а не просто "уже проголосовавшие 0"), источник
  пересоздаётся отдельной карточкой со своими голосами и прежней привязкой
  к автору (`author_participant_id` сохранён в снимке).
- Ограничение: снимок хранит только последний шаг. Если карточку склеили,
  потом ещё раз склеили с чем-то третьим — разъединить получится только
  последнее слияние, до самого первого состояния добраться нельзя. Кнопка
  разъединения (🔀) показывается только если у карточки вообще есть
  актуальный `last_merge_snapshot`.

## Про сохранение результата при завершении ретро

Изначально на этапе 9 предполагался просмотр архива через отдельный экран
импорта (см. историю решений выше про историю досок) — вместо этого сделали
проще и привязали сохранение прямо к моменту завершения:

- `components/FinishRetroModal.tsx` — открывается по кнопке
  🏁 "Ретро закончилось" (модератор, плавающая кнопка в углу экрана слева от
  переключателя темы). После подтверждения показывает три способа сохранить
  результат: **JSON** (`lib/archive.ts: buildExportPayload` — те же функции,
  что использовались в раннем варианте архива), **ссылка** на доску
  (копирование в буфер) и **PNG-скриншот** самой доски.
- Скриншот через `html2canvas`, добавлен в зависимости — после раскладки
  файлов обязательно `npm install`, иначе `import('html2canvas')` не
  найдёт модуль. Библиотека подключена динамическим `import()` внутри
  обработчика клика, а не статическим импортом в начале файла — она нужна
  только в момент, когда кто-то реально нажал "Скачать картинку", незачем
  тащить её в общий JS-бандл каждой загрузки страницы.
- Область для скриншота помечена `id="retro-board-capture"` на самом гриде
  столбцов в `Board.tsx` — `html2canvas` захватывает именно её, а не всю
  страницу целиком (без шапки, кнопок и т.д.).

## Про поле "Голосов на участника" на странице создания

Убрано из формы `/create` (2026-08-31) — раз это же значение можно
поменять после создания доски в "⚙ Настройки", дублировать выбор на входе
избыточно. Весь код поля (state, валидация, JSX) не удалён, а закомментирован
прямо в `app/create/page.tsx` — на случай, если решение пересмотрят.
