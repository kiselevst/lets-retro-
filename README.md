# Let's Retro

Ретро-доска команды. Миграция с HTML-прототипа (`window.storage` + polling) на
Next.js 15 + Supabase (Realtime, без polling).

## Статус миграции

- [x] Этап 1 — скелет репозитория, Supabase-клиент, первая SQL-миграция
- [x] Этап 2 — RLS-политики (открытые, без Auth — осознанное решение для MVP), `lib/types.ts`
- [x] Этап 3 — лендинг, создание доски, вход в комнату по ссылке / коду
- [x] Этап 4 — чтение доски (столбцы + карточки + участники) через Supabase Realtime, без polling
- [ ] Этап 5 — CRUD карточек и голосование
- [ ] Этап 6 — drag&drop склейка, SMART, экшн-айтемы, «ретро закончилось»
- [ ] Этап 7 — таймер, highlight-режим

## Запуск локально

1. Создать проект на [supabase.com](https://supabase.com).
2. Скопировать `.env.example` → `.env.local`, вставить `NEXT_PUBLIC_SUPABASE_URL` и
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` из Project Settings → API.
3. Применить миграции из `supabase/migrations/` **по порядку** (0001 → 0002 → 0003) —
   через Supabase CLI (`supabase db push`) либо вставляя содержимое каждого файла
   в SQL Editor в дашборде и выполняя одну за другой.
4. `npm install`
5. `npm run dev` → http://localhost:3000

## Деплой на Vercel

1. Импортировать репозиторий в Vercel (Import Git Repository).
2. Добавить те же переменные окружения (`NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`) в Project Settings → Environment Variables.
3. Deploy. Дальше — `git push` на нужную ветку деплоит автоматически.

## Про безопасность (этап 2)

RLS включён на всех таблицах, но политики открытые (`USING (true)`) — без
Supabase Auth у Postgres нет возможности проверить, кто именно шлёт запрос
(anon-ключ общий на всех). Это осознанный выбор для MVP с доверенной командой,
совпадающий по уровню защиты с исходным прототипом на `window.storage`.

## Про identity (этап 3)

Без Supabase Auth: при создании доски или входе по ссылке/коду создаётся строка
в `participants`, а её `id` кладётся в `localStorage` браузера (ключ per-board).

## Про Supabase-клиент без generic-типизации

`lib/supabase.ts` намеренно не типизирован через `createClient<Database>(...)` —
ручное (не сгенерированное `supabase gen types`) описание схемы приводило к
ложным ошибкам компиляции на полностью корректных данных. Типы из `lib/types.ts`
(`CardRow`, `ColumnRow` и т.д.) используются как обычные ручные касты
(`as CardRow[]`) в хуках, без завязки на внутреннюю generic-механику клиента.

## Про Realtime (этап 4)

Каждая таблица, за которой нужно следить в реальном времени, должна быть
добавлена в publication `supabase_realtime` — это отдельная миграция
(`0003_enable_realtime.sql`), не забыть при добавлении новых realtime-таблиц
на следующих этапах (`votes`, `timer_state`). Хуки (`useBoardData`, `useCards`,
`useParticipants`) при любом изменении просто перезапрашивают данные целиком —
для размеров одной ретро-доски это проще и надёжнее точечного патчинга
состояния, а разница в нагрузке не имеет значения.

**Важно:** добавление карточек, голосование и вся интерактивность — это уже
этап 5. Сейчас доска только читается и обновляется в реальном времени при
изменениях, сделанных напрямую в Supabase (например, через SQL Editor).
